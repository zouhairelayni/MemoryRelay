# MemoryRelay v3.5.0 — Full-library discovery and structured memory metadata

**Date:** 2026-11-23
**Development baseline:** v3.4.7
**Consolidated installer input versions:** v3.3.0, v3.3.8, or v3.4.7 (clean Git worktree required)
**Commit title:** `feat(memoryrelay): full-library discovery and structured memory metadata (v3.5.0)`

## Problem and design contract

The old MCP `search` tool returned at most 20 memories per call, with no pagination. Its results included the full memory bodies. The owner memory list also imposed a hard 500-entry listing cap. That made targeted research into the user's library expensive and could hide relevant historical records. Build versions, platform, language, and technology stack were mixed into the old comma-separated context tags or not recorded at all.

The new model separates **discovery metadata** from **original memory content**. A memory's full Markdown is read only after choosing the index entry by ID. The user-approved MemoryRelay ribbon logo, PWA icon assets, and startup welcome sequence are unchanged.

## Data migration: additive and no inferred facts

`ensureSchema()` adds two non-null columns when missing:

- `description TEXT NOT NULL DEFAULT ''`
- `metadata TEXT NOT NULL DEFAULT '{"app":"","platforms":[],"feature":"","version":"","languages":[],"stack":[]}'`

No original Markdown, rule flags, context tags, history, source, or timestamps are overwritten. A legacy row without an explicit description displays a faithful excerpt from its existing first Markdown title/line. Versions, technology stacks, programming languages, and platform facts are **never invented or auto-filled**. Editable metadata fields are:

| Field | Storage | Visual chip | Meaning |
| --- | --- | --- | --- |
| `app` | string | Indigo | Product/project name |
| `platforms` | string list | Cyan | PWA, web, mobile, backend, etc. |
| `feature` | string | Mint | Feature being documented |
| `version` | string | Amber | Verified build or release identifier |
| `languages` | string list | Rose | Programming languages |
| `stack` | string list | Slate | Technology components/frameworks |
| `description` | 0–280 characters | Plain text | Searchable human-written summary, or excerpt fallback |
| `tags` | Existing comma-separated string | Context tags | Maintains the old 5-tag and reserved `rules` semantics |

No automatic scripts run from memory content. The React Markdown renderer constructs text nodes, not injected HTML. Fenced blocks and inline commands remain plain text with copy actions.

## MCP discovery tools

All tools are permission checked against the connection's existing read/write/full access.

- `list_memories({limit:100,offset:0,app:"MemoryRelay"})`: Browse all matching memories, no query required, with compact index records. Returns `total`, `count`, `limit`, `offset`, `next_offset`, and `results`.
- `search({query:"memory search",limit:100,offset:0,platforms:"pwa"})`: Keyword search across content, descriptions, context tags, and typed metadata; **query is required** (empty string lists all). Page until `next_offset === null`.
- `get_memory({memory_id:"..."})`: Fetch a selected memory's entire Markdown content with description and metadata. Includes code snippets without executing them.
- `recent({n:20})`: Keeps the existing up-to-20 behavior and now includes structured metadata and descriptions alongside full text.
- `remember({text:"**Title**\n- *Detail:* value",description:"...",tags:"...",metadata:{...}})`: Saves a memory with independent structured labels, subject to the live owner-configured estimated-token limit.
- `update_memory({memory_id:"...",description:"...",metadata:{version:"v3.5.0"}})`: Partial metadata updates; omitted fields are preserved, `""` or `[]` clears a field. Rules remain owner-only.
- `get_memory_settings({})`: Reports current limit and the supported discovery tools, Markdown formats, command snippets and metadata fields.

The `tools/list` tool descriptions, input schemas, and MCP `initialize.instructions` explicitly advertise all capabilities. **After deployment reconnect/refresh MCP clients**, because they may cache the old tool list or descriptions from before v3.5.0.

## Owner API, UI and imports

Owner `GET /api/memories` now accepts `q`, `limit`, `offset`, `rule` (`all|rules|memories`), `app`, `platforms`, `feature`, `version`, `languages`, and `stack`. The server applies the filters across the whole library before pagination. Default page size: 30. `GET /api/memories/:id` fetches one complete memory and requires the existing owner session. The React list has a **Show more** action, supports incremental loading, and displays total matches. The add/edit form offers a short-description field and six typed-label fields; cards render color-coded badges and still show legacy context tags.

JSON export includes the two new columns and reimport preserves them. Invalid metadata aborts an import before any destructive replace. Rule memories are still excluded from replace imports. Housekeeping also refuses to merge a versioned or app-labeled memory with a memory carrying a different or missing version/app; separate build/release records remain separate.

## Intentional limitations

- Indexed search uses bounded SQL substring matching, **not semantic/embedding search** or an AI-generated narrative description.
- `offset` pagination can shift during concurrent additions/deletions. For audit-stable snapshots, export a backup or pause edits during traversal.
- Unknown metadata is left blank. Existing memories are not automatically relabeled with guessed project names or release versions.
- Tool-list updates are visible only after deploying the new Worker source and reconnecting clients that cache tools.
