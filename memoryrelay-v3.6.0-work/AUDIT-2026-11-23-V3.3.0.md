## Limits and tradeoffs

- Memory token counts are **estimates, not exact model-tokenizer counts**. The shared conservative estimator uses the larger of UTF-8 bytes / 3 and word count × 1.3, rounded up. This prevents a model-dependent token library from becoming a new runtime dependency. A separate maximum of 32,000 UTF-16 characters per memory bounds input/storage cost. Existing memories longer than a subsequently lowered limit are not altered and remain readable.
- The authenticated owner may choose 100–8,000 estimated tokens per memory without changing or deploying code; further expansion past the safety cap would still require an implementation change.
- The application remains owner-operated. `get_memory_settings` in MCP is **read-only**; agents cannot change their own limits.
- Browser/OS control of `showPicker()` varies. On browsers without the API or where opening is refused, the ordinary native HTML `<select>` is shown. It is not possible to guarantee the same OS popup on all browsers.
- Installed-PWA detection uses `(display-mode: standalone)` and iOS `navigator.standalone`; browser tab and installed standalone runtime behavior was code-reviewed, not executed on a physical Android/iOS device.

## Rollout and rollback

- Version bumped from **3.2.0 → 3.3.0** (package, lockfile, MCP server version). Service-worker cache bumped to v6. No destructive migration: the new runtime memory limit is an additional row in the existing `config` table.
- Inspect any old memories before lowering the limit; such records remain readable but will have to meet the current limit to be edited.
- Review the patch on the user's real Git branch, run tests and `npm run build`, commit/push there; do not auto-deploy from an unreviewed production branch. Rollback is a normal Git revert; saved memory text is never rewritten during this upgrade.
